## 工具已经实现到哪里

`src/hangtian/autonomous.py` 实现六种自由窗口操作：读取、按行分段概览、统计、时间轴质量检查、持续越阈事件、连续全零区间。`src/hangtian/pi_bridge.py` 将这些操作暴露给 Pi 的 `telemetry_query`，并提供 `submit_report`。这里是六种计算能力、两个模型可调用的入口。模型自行选择记录、通道、窗口、阈值和比较方法。工具不是固定解题流程。

所有窗口是原始采集行号、从零开始、左闭右开；读取最多返回 512 行并明确给出下一页起点，不排序、不静默去重或填补。只有已审核公开目录中的记录允许查询。没有任意代码执行、终端、文件读取、网络检索工具。模型不接触材料包的私人参考事实、评分规则、故障标签和生成历史。

工具范围目前有限：没有模型可执行的 Python，没有绘图、积分、拟合等专用工具。若任务确实需要当前工具无法完成的计算，应记录为工具环境问题，不能直接归为模型能力失败。

## 运行

服务器根目录为 `/home/xjshang/hangtian_material_pipeline`。提交 `scripts/run_qwen_pi.sbatch`：申请一张 A100 80GB、8 CPU、110GB 主机内存，上限 4 小时。作业启动本机回环地址上的 vLLM 服务，最多并发运行四个独立 Pi 会话，覆盖 T01–T15，之后运行 T01/T05/T12 三个无数据对照；结束或异常时关闭模型服务。不同会话不共享消息或工具观测。最大时限是保护上限，完成后立即释放资源。

`configs/pi_qwen35_27b.example.json` 固定本轮抽样参数、上下文和预算。Pi 的思考级别为 off；每个实际推理请求还校验 `chat_template_kwargs.enable_thinking=false`。非回环地址、其他模型、思考模式请求均被拒绝。凭证不读取、不传递。

每题上限 20 次模型请求、80 次数值工具尝试、20 分钟；单次输出上限 8192 token，上下文上限 65536 token。达到限制而未答完须记录为未完成，不能自动评分为正确。无数据对照每题一次请求，无数据工具；它只用于检查是否能靠题面推测关键结论，不用“不能提供引用”这样的必然失败证明题目质量。

结果目录 `runs/pi_qwen35_nothinking_001/job_<SlurmID>/` 下分别保留每题公开输入、会话边界、工具调用、模型输出（不保留隐藏思考）、请求参数、服务实际返回模型标识及用量、结构化答案和证据重算结果。历史失败尝试使用独立目录，不覆盖。

## 怎样判定质量

1. 运行是否完成、能否正确调用工具，是执行环境检查。
2. 重算每次观测并检查引用是否真实，是证据完整性检查。
3. 按既有内部结果标准逐题审核测量定义、数字、比较和推论，是语义审核。不同有效分析路线均可接受；不要求命中参考查询。
4. 结合轨迹分析题目是否泄露结论、是否有大量步骤提示、工具或评分是否妨碍有效分析，是任务质量审核。

前两项通过不等于后两项通过。一次模型运行也不能单独确立题目的普遍难度或区分度。此轮没有训练、微调或修改公开题目。

## 未提交会话的补充诊断

原始自主运行保持 20 次请求上限，不补写答案或覆盖失败轨迹。对未提交的题目，可以用 `scripts/run_qwen_pi_reporting.sbatch <已完成基线目录>` 运行独立的收束诊断：同一 Qwen 模型、相同抽样设置、关闭思考模式，只提供原题和该 Agent 先前已查询到的观测，一次响应内调用 `submit_report`。不提供新测量、参考事实、评分要求或解题路径，不开放查询工具。

诊断入口会重新执行保存的查询，校验先前观测未被篡改；拒绝不同题目、已提交的基线和未完成的 15 题作业。输出保存在 `runs/pi_qwen35_reporting_001/job_<ID>/`，与基线分开。这个条件改变了会话组织和提交提示，即使形成正确报告，也只能表明已有证据在明确收束要求下的可用性，不能计入原始自主完成率或证明单纯增加一轮就能解决问题。

基线第一版仅记录到达数值后台的工具结果；被 Pi 参数校验提前拒绝的调用只能从模型发出的参数与后台日志缺口中识别，不能声称保存了这类调用的完整反馈文本。后续入口增加 Pi 的 toolResult 事件日志。20 次额度耗尽后，Pi 可能把本地请求拦截包装为 `Connection error`；应结合请求计数、预算与服务日志判断，不能直接归为服务器网络断线。

实现参考：[Pi SDK](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/sdk.md)、[Qwen3.5-27B 官方模型说明](https://huggingface.co/Qwen/Qwen3.5-27B)、[vLLM Qwen3.5 工具调用配置](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html)。实际 SDK 版本及接口以服务器安装的 0.87.1 为准。

## DeepSeek-flash 重跑：协议 v2（作业165942）

用户于2026-10-09重新授权使用此前提供的DeepSeek密钥，执行原批次T01–T15。入口为 `scripts/run_deepseek_pi.sbatch` 与 `scripts/run_deepseek_pi_job.py`，配置为 `configs/pi_deepseek_flash_budget80.json`。批次固定为 `runs/autonomous_tasks_final_001`，不使用另外扩展的100题批次，也不注入Qwen旧轨迹。每题独立Pi会话，上限80次模型请求、320次查询尝试、2小时，预留3次报告请求；最多4题并发。第一题由程序作为连接检查，成功执行后自动调度其余14题，不需要人工逐题干预。

只允许 `https://api.deepseek.com` 上的 `deepseek-flash`；每次实际请求强制 `thinking: {"type": "disabled"}`，禁用自动重试和模型回退。密钥由服务器仓库外的0600文件读入模型进程环境，不传给数值工具服务、不写入快照。远程执行必须显式提供 `--allow-remote --allow-data-egress`。会发送公开题面、工具定义、该Agent查询得到的数据和会话历史；不发送私有参考答案、评分规则或故障标签。

协议v2修复了两项已核实的问题：最后一个获准调查响应的查询不再因计数自增被提前拒绝；后台工具错误改为Pi真正的 `isError=true`。进入报告阶段时也同步收窄Pi实际执行工具集合。没有修改题面、调查提示词、数值操作、参考数据和评分规则。不同于本地Qwen的精确tokenizer，这里使用API返回的上一轮输入用量，加新增内容UTF-8字节数及余量，保守估计上下文；不删改旧证据。实验上限仍为131072，100000触发报告，并非宣称这是服务商模型的最大上下文。Flash请求保留temperature=0.7，省略其不支持或无需发送的Qwen专用参数。因此与旧Qwen结果的比较同时受模型、协议修复和上下文计数差异影响，不能作为纯模型差异的消融实验。

执行前本地及HPC的111项Python测试、9项Node检查通过；HPC离线CLI通过。实际Pi SDK还通过5响应的离线传输测试：错误反馈、最后调查响应、进入报告、拒绝空引用、修正提交均按预期发生，无密钥落盘。该fixture没有外部推理，不计入15题成绩。

作业165942已提交CPU分区，申请4核、12GB内存，不申请GPU。结果保存在 `runs/pi_deepseek_flash_budget80_001/job_165942/`。程序在整批结束后自动重算实际查询的数值；提交数、数值核对和语义正确性分开，后者仍需逐题审核。本节只记录启动，不宣称完成或通过。
